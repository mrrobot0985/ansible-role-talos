# Generated Output

After running the role, the `.talos/` directory appears at the playbook root. It holds machineconfigs, patches, secrets, kubeconfig, and — when `talos_generate_docs: true` — browsable documentation.

## `.talos/` — Machineconfigs and Patches

This directory contains everything required to install, review, and operate the cluster.

```text
.talos/
├── config/
│   ├── base/
│   │   ├── controlplane.yaml     # Base control plane config
│   │   ├── worker.yaml           # Base worker config
│   │   └── talosconfig           # Talos client config
│   └── secrets/
│       └── secrets.yaml          # Encrypted secrets bundle
├── patches/
│   └── nodes/
│       ├── cp-1.json             # Per-node RFC6902 JSON patch
│       ├── cp-2.json
│       └── worker-1.json
├── generated/
│   ├── cp-1.yaml                 # Final machineconfig (reviewable)
│   ├── cp-2.yaml
│   └── worker-1.yaml
└── kubeconfig                    # Final Kubernetes admin config
```

- **`config/base/`** — The raw output of `talosctl gen config`. These are your templates.
- **`config/secrets/`** — Sensitive material generated by `talosctl gen secrets`. Protect this directory.
- **`patches/nodes/`** — One RFC6902 JSON patch per node. These are the exact changes that will be applied to the base config.
- **`generated/`** — The final machineconfigs after patching. Review these before a real deployment.
- **`kubeconfig`** — The Kubernetes admin config, rewritten to use the VIP when one is configured.

## `.talos/generated/` — Documentation and Structured Data

When `talos_generate_docs: true`, the role creates documentation under `.talos/generated/`. This output is safe to delete and recreate; it is not committed to version control.

It contains two kinds of output: human-readable Markdown pages suitable for serving with MkDocs, and structured YAML files that follow a NetBox-style DCIM schema for downstream automation.

```text
.talos/generated/
├── mkdocs.yml              # MkDocs configuration (Material theme)
├── docs/
│   ├── index.md            # Site homepage
│   ├── cluster.md          # Cluster-wide summary
│   └── nodes/
│       ├── cp-1.md         # Detailed per-node page
│       ├── cp-2.md
│       └── worker-1.md
└── data/
    ├── cluster.yml         # Cluster-wide structured data
    └── nodes/
        ├── cp-1.yml        # Per-node structured YAML
        ├── cp-2.yml
        └── worker-1.yml
```

### Markdown pages (`*.md`)

The Markdown files are ordinary prose documents. They contain tables, lists, and headings that describe the cluster as it exists at the moment the role ran.

- **`docs/index.md`** — A landing page with the cluster name, Talos version, and a link to the cluster summary.
- **`docs/cluster.md`** — A single page aggregating every control plane and worker, the VIP, DNS settings, NTP sources, and any cluster-wide extensions or kernel arguments.
- **`docs/nodes/<hostname>.md`** — One page per node. Each page lists discovered hardware facts, the selected install disk, network interfaces and addresses, applied patches, and the node's final role in the cluster.

These pages are generated from live facts, not from static inventory variables, so they reflect the actual state of the nodes at the time of generation.

### Structured data (`data/*.yml`)

The YAML files in `data/` hold the same information in a machine-readable shape. They are useful for feeding into external inventory systems, CMDBs, or NetBox.

- **`data/cluster.yml`** — High-level cluster attributes: endpoint, VIP, DNS domain, NTP servers, and the list of member nodes.
- **`data/nodes/<hostname>.yml`** — Per-node DCIM-style records. Each file contains sections for `device`, `interfaces`, `ip_addresses`, `disks`, and `custom_fields`, mapping cleanly onto NetBox's object model without requiring any vendor-specific extensions.

Because the schema is flat and explicit, you can ingest it with a simple Jinja2 template or a small Python script without parsing Markdown tables.

## Browsing the Documentation

The `.talos/generated/` directory is a self-contained MkDocs site. To preview it locally, run:

```bash
cd .talos/generated
mkdocs serve
```

The `mkdocs.yml` file is generated with the Material theme and sensible defaults. If you want to change the theme or add extra navigation, edit `mkdocs.yml` and re-run `mkdocs serve`. The Markdown files themselves are plain CommonMark with Material extensions, so they also render correctly in GitHub, GitLab, or any other Markdown viewer.

Because `.talos/` is gitignored, the documentation does not pollute your repository. You can archive it as a build artifact, sync it to a web server, or commit it to a separate docs repository if you prefer.
